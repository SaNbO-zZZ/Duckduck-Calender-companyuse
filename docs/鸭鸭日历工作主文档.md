### 2026-11-13 v4.0.0 官方 challenge 响应能力复核

为排除回调 payload 误差，受控临时启用 `dutyCardCallbackBridge`，向妙搭 runtime 发送不含员工身份的 `url_verification` 合成请求，随后立即停用并回读 disabled。runtime 成功接收请求并在 dispatch 日志中记录 `type=url_verification`、`challenge` 和 `token`，但 HTTP 响应仍为固定的 `code=200 / message=success`，没有返回 challenge；飞书控制台因此继续提示“Challenge code没有返回”。

进一步核对本地 `@lark-apaas/nestjs-trigger` 官方运行时包：`POST /innerapi/automation/invoke` 的公开合同是“接收成功、异步执行”，响应固定为 200 接收状态；handler 返回值只进入 action 观测日志，不会成为 Webhook HTTP 响应。这与线上 dispatch 日志一致，说明在当前妙搭 full_stack runtime 中无法通过业务 handler 补出飞书 URL 校验响应。官方事件目录仍将 `card.action.trigger` 定义为 bot 长连接/回调订阅能力，项目本地插件清单仍只有多维表格和发消息插件。

可执行下一步：保留 `dutyCardCallbackBridge` 和 `duty16hReminder` 为 disabled；由妙搭平台提供 challenge 原样响应配置、Webhook 响应体合同或官方事件桥接插件后，再重新保存飞书开发者服务器地址。若平台改为只支持长连接，则按官方 Feishu SDK 的长连接合同另建受控适配，不把 `lark-cli event consume` 常驻进程当作应用运行时。

本轮新增 `url_verification` 解析拒绝回归，`npm run type:check`、`npm run build:server`、`node tests/duty-card-callback.cjs` 和 `git diff --check` 通过；未发送真实员工消息。

### 2026-11-13 v4.0.0 回调阻塞影响与替代路径调研

影响范围已拆分确认：妙搭运行时缺少飞书 challenge 同步响应合同，只阻塞 `card.action.trigger` 的实时入站换班机器人闭环（卡片点击、即时 toast/卡片更新和自动写入 `duty_exchange_request`）；不影响日历展示、妙搭数据库、7 条人员—鸭鸭绑定、16:00 cron handler、单人提醒模拟能力或应用内登录访问。当前两个触发器继续 `disabled`，不会产生真实员工消息。

官方能力对照：飞书回调要求开发者服务器在校验和交互请求中同步返回结果；卡片回调需在 3 秒内返回 HTTP 200。妙搭当前 `POST /innerapi/automation/invoke` 是异步接收合同，HTTP 层固定返回接收状态，因此不能把业务 handler 的返回值当作 challenge 或卡片响应。

已调研的替代路径按兼容性排序：

1. **妙搭应用内打开链接（推荐）**：卡片按钮改为 `open_url`，携带一次性换班请求标识，进入妙搭已登录页面；页面读取当前用户和请求后完成确认/拒绝，写入现有状态机和 `duty_override`。它不需要 WebSocket、开发者服务器或 challenge 响应，最符合当前妙搭工程边界；代价是不能在原卡片内即时更新，需要用户进入页面完成操作。
2. **飞书审批 + 妙搭 `feishu-approval` 自动化**：把换班确认变成正式审批，使用审批实例/任务状态触发妙搭动作。官方事件支持 `PENDING`、`APPROVED`、`REJECTED`、`CANCELED` 等状态；优点是有审计和重试，代价是审批体验更重、不是即时卡片回传，且需要新增审批定义和权限。
3. **独立官方 Feishu SDK 长连接桥接**：使用官方 SDK `WSClient` 接收 `card.action.trigger`，再通过受支持的妙搭 OpenAPI/数据库能力写回。技术上可行，但会引入妙搭之外的常驻运行时，不符合当前“妙搭本地工程作为唯一运行时”的约束；除非后续明确授权架构例外，否则不实施。
4. **传统公网 Webhook 中继**：由独立公网服务处理 challenge 和回调，再转发到妙搭 Webhook。可完成控制台绑定，但同样引入普通后端、密钥和新的可用性边界，当前不采用。

建议下一步优先把换班入口改成“妙搭应用内打开链接 + 登录后确认”的受控闭环；若业务必须保留卡片内即时反馈，再评估独立官方 SDK 长连接桥接，并先取得架构例外授权。调研依据见飞书官方[回调概览](https://open.feishu.cn/document/event-subscription-guide/callback-subscription/callback-overview)、[接收和处理回调](https://open.feishu.cn/document/event-subscription-guide/callback-subscription/receive-and-handle-callbacks)、[卡片交互配置](https://open.feishu.cn/document/feishu-cards/configuring-card-interactions)、[事件订阅](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/event-subscription-guide/event-subscriptions)和[审批状态变更事件](https://open.feishu.cn/document/ukTMukTMukTM/uIDO24iM4YjLygjN/event/common-event/approval-instance-event)。
