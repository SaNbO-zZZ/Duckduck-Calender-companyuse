## 正式切流顺序

1. **预备正式站。** 取得正式部署与域名配置的逐项批准。保存两端原主页、企业导航目标/范围、旧 release、调度和原表权限证据。在生产目标设置服务端变量、独立会话凭证、正式飞书回调，先以 `DUCKY_READ_ONLY=1` 验证。负责人在 Cloudflare 配置 Vercel 为正式域名实际分配的 DNS 目标。检查权威 DNS、HTTPS、真实 OAuth、原租户授权、月历、公约与换班深链。以预定上线提交的真实构建和部署 ID 留档。
2. **冻结与排空。** 在 16:00 窗口以外交接。新端保持只读，先验证旧端每个实例均已具备数据库守卫、先前 release 的调用与外部直写已结束。经批准停旧调度并回读，再运行旧库 `drain.sql`。用旧窗口与旧直达受控请求核实写入被拒。逐笔复核残留工单、Base 外部回执和消息状态；遇到不确定投递要保留去重依据。工单清零后运行 `seal.sql`，回读 sealed 并验证九表的写入屏障。任一证据缺失即暂停。
3. **终算与补导。** 封存后保全九表、加密或受访问控制的人员对照、目标库及新独有表、原 Base 记录和发布配置。按 ID 与字段比较源独有、目标独有及同键变化。当前三条历史差异必须以窗口快照再次确认。只有获批增量可补导；冲突、中途修改、未知身份、在途换班或非预期目标记录逐项裁定。补导失败回执只保存历史，不驱动重发。重复导入须幂等，复跑登记对账并复查两端排班及人员绑定。
4. **原应用入口。** 沿用飞书自建应用 `cli_aa35caedff78dcc5`、原图标和可用范围。检查桌面默认外露导航的实际类型：固定 URL 更新同一条目的目标，应用引用则发布同一应用的桌面主页。旧记录显示桌面 URL 曾独立下发。同步同一应用的移动主页，保留原导航位置和配置快照。普通员工与管理员分别从桌面原左栏、手机工作台或原应用进入，及从已有窗口重新打开。确认为正式域名、真实账号、月历及公约均可读，全程无 Vercel 账号或预览码要求；另测收藏和旧消息深链。手机可见范围与是否默认固定在底栏分别核实。
5. **交接业务写入与提醒。** 旧写端保持 sealed。原入口及终算通过后，按批准将已验收部署切换到可写配置，复核实际部署 ID、已打开的旧窗口仍拒绝写入及新版写入权限，再开放新版正常写入，以已批准的人员验四类登记、原表真人字段和 Mentor/人事回执、真实双方换班、公约已阅幂等。使用 `ducky_scheduler.enqueue_reminder(true)` 取得请求编号，核对对应 HTTP 200、`recipientResolved=true`、`sent=false`。核实旧任务已停，再按调度批准启用 `ducky-duty-reminder-1600`。首次 16:00 将 cron 时间、请求 ID、HTTP 回执、当日有效值班人、唯一投递记录、飞书受理与手机到达时间对齐。全员知会、节日主题各自按批准操作。

## 回退与旧版退役

**回退。** 切换入口和恢复写入是两个不同操作。先停新调度、新业务写入，核对已开始的请求和外部回执，记录两端当日幂等键。新端尚无写入时，验证旧端数据及去重状态再受控恢复旧入口与唯一写端。若已有新写入，先保全 Supabase 新增/变更、原 Base 与飞书受理记录。在隔离恢复库反向映射人员、登记编号、换班、覆盖与投递状态，并确认恢复后旧任务不会重复发信。只在旧库能表达所有仍在用的状态且对账一致后重新开放旧写入。无法映射或回执不明时，保持只读或修复新版后向前恢复。保留新版专有的公约、已阅及主题数据。

**退役。** 新版上线并经原入口、业务写入、首次正式提醒和回退复核后，尽快退役旧的妙搭运行时。先解决历史消息、最近使用中的蓝色入口及收藏；对未结换班逐条确认可从新版带原编号打开。无法配置重定向时，提供旧地址的只读迁移提示或其他经核准的承接方式，并核实访问。确认所有数据读写、名单刷新及公约同步已脱离旧运行时。保全旧 release、源码、文件对象清单、可信备份及恢复证据。管理后台确认删除对象和级联范围；如果只能连同共享资源删除，暂停该动作。保留飞书原自建应用、机器人、通讯录授权、四张原 Base 表、Wiki/Docx、公约与更新日志、正式域名和 Supabase。删除后复查原入口、原表读取、公约同步、静态素材、调度健康和单次投递记录，归档退役时间与结果。
